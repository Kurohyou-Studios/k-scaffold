# Attribute mixin → Foundry DataField mapping

Each Roll20 attribute-holder mixin maps to a Foundry `DataField` in generated `defineSchema()` as follows: `text`/`hidden` → `StringField`; `textarea` → `HTMLField` by default (rich text), with an explicit opt-out falling back to plain `StringField`; `number`/`range` → `NumberField`, passing `min`/`max`/`step` straight through from the mixin call and always defaulting `integer: false` (never inferred from `step`); `select`/`radio`/`radioGroup` → `StringField`/`NumberField` with `choices` enforced, since every option set is compile-time static today (no dynamic option population exists on either target yet — see "Not yet specified" on the Foundry export map). `checkbox` is the one mixin whose Foundry field type is not fixed: it mirrors the JS type of the `value` argument given at the call site — no `value` → `BooleanField` (`false`/`true`); a numeric `value: N` → `NumberField` (`0`/`N`); a string `value: S` → `StringField`, stored as `"0"`/`S`. This keeps existing sheet-worker math (which assumes `0`/`1`-shaped checkbox values) working unchanged: the alias layer is responsible for handing authored code back the exact JS-typed values it gets today, translating at the boundary regardless of what the schema stores underneath.

Named attribute-backed display elements (`span`/`div`/`img` with `obj.name` set) get **no schema field of their own** — they're always treated as derived/computed values (produced by `prepareDerivedData()`), not stored state, since nothing in the mixin signature today distinguishes "mirrors a stored attribute" from "shows a computed value."

`compendiumAttributes`/`compendiumContainer` (Roll20's drag-and-drop-a-compendium-item hidden-attribute convention) are suppressed entirely on Foundry output — no hidden fields, no wrapper — because Foundry's own compendium system works fundamentally differently (direct Actor/Item document instances, not drag-and-drop attribute pairs) and is out of scope per [0017](0017-compendiums-and-active-effects-deferred.md). `compendiumContainer`'s wrapped block content still renders normally on Foundry; only the drop-target wrapper and its hidden attributes are dropped, so arbitrary sheet content isn't silently lost just for having been nested inside one.
