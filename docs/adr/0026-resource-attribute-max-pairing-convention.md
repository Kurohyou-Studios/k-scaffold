# Resource attributes are a `_max`-suffix pairing convention, detected purely at runtime by the alias layer

For `attributes.hp.max` to resolve identically on both targets (ADR 0024 already gives every numeric Foundry attribute a `{ value, max }` shape), Roll20 needs an equivalent concept — but no new mixin argument, cascade record, or compile-time declaration is introduced for it. A **resource attribute** is any attribute `<name>` for which a second, completely ordinary attribute `<name>_max` also exists on the sheet (declared with the same `+number`/`+range` mixins as anything else); `_max` becomes a reserved pairing suffix, detected by `attrHandler`/`repeatHandler` purely by checking at access time whether the counterpart attribute exists. `hp_max` needs no special declaration to be written, read, or triggered — it behaves exactly like any other flat attribute; the only new behavior lives entirely in the proxy.

For every attribute, `.value` is now always readable (`attributes.hp.value === attributes.hp`'s current value), whether or not it's paired. `.max` only resolves when the pairing exists; otherwise it's `undefined`, same as reading any other nonexistent attribute. Writes mirror this: bare `attributes.hp = 5` and `attributes.hp.value = 5` both write only the current value, matching today's flat-attribute-write semantics; `attributes.hp.max = 20` and `attributes.hp_max = 20` are equally valid, both writing through the same underlying flat attribute and its existing triggers. The same convention generalizes into `repeatHandler` for row fields (`row.damage`/`row.damage.max`), not just top-level attributes.

On Foundry, the presence of a `<name>_max` pairing is the signal the generator uses to mark that attribute bar-eligible (`trackableAttributes`/`system.json`) — no second, separate declaration, since a real Roll20-side max is exactly what makes a `{value,max}` field meaningful as a token bar.

**Accepted cost**: for a paired attribute, `attributes.hp` can no longer be a raw JS number — reading `.max` off it requires returning an object, not a primitive. The wrapper uses `Symbol.toPrimitive`/`valueOf` so arithmetic, loose comparison (`==`), and template-literal interpolation all still behave as before; `typeof attributes.hp === 'number'` and strict `attributes.hp === 5` are the two things that change for paired attributes only. Unpaired attributes (the vast majority of any sheet) are completely unaffected — this cost is scoped exactly to attributes an author opted into pairing by declaring a `_max` counterpart.

**Considered and rejected**: a new mixin argument (e.g. `pooled: true` or a formula-valued `max`) to declare resource attributes explicitly at the call site. Rejected because it duplicates information the pug markup already expresses once the author writes both `+number({name:'hp'})` and `+number({name:'hp_max'})` — nothing about *this* attribute needs to know about pairing at declaration time; the proxy can discover it from what already exists.
