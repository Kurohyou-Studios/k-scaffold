# Foundry sheets bypass native form submission and never run reactions

The generated Foundry sheets (a shared `KScaffoldSheetMixin` applied to both `ActorSheetV2` and `ItemSheetV2`, with per-mode / per-Item-type subclasses that carry only static data) do **not** use `DocumentSheetV2`'s native form submission. Instead the mixin overrides `_onChangeForm`: each changed input becomes a single alias-layer `set()` for that attribute, flushed once. Native submission calls `document.update(expandObject(formData))`, which cannot represent our storage shapes — an `ArrayField` row input like `system.attacks.2.damage` casts to a sparse array that replaces the whole array (dropping other rows, defaulting the row's other fields, or failing validation), and Item-backed row inputs belong to other documents entirely. The alias layer already resolves all three shapes (plain, array row, Item row) per #158, so routing through it gives change events and button clicks (`kButton` action) one write path and gives `mockFoundry.js` one seam to fake. We rejected patching the native pipeline (`_processFormData` merge into `_source`, the dnd5e workaround, plus separate Item routing) as two Foundry-internals overrides duplicating logic the alias layer already owns.

A sheet-originated change **only writes the value** — it does not run Roll20's `accessSheet`-style `change:` cascade. Derived values come from `prepareDerivedData()` (ADR 0028), and `triggeredFuncs` are deferred to a document-level hook. Running them from the sheet would make behavior depend on the edit path: token-bar edits, macros, and other modules calling `actor.update()` would silently skip them. The sheet is one writer among several; reactions belong on the document.
