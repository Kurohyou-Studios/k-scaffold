# Cross-document access is explicit, not shared reads

Modes are alternative *kinds* of character (player character, NPC, vehicle); any one character is exactly one mode, so there is no mode-to-mode data traffic to design for. The only cross-document need is character-to-character: one character invoking behaviour on another. That is handled through the existing `k.send` RPC pattern (`lib/scripts/utility.js`) on both targets: a registered function on the target character is invoked with explicit, serialized arguments, rather than one character reading another's attributes directly. Embedded Items reading their owning Actor's data are the one exception — a genuine parent/child structural relationship — and read transparently through the same alias-layer proxy as the Item's own fields, mirroring how Roll20 sheet-worker code inside a repeating row already reads non-repeating (character-level) attributes through the same flat `attributes` object with no special-casing.

*Amended 2026-09-20 (#159):* the original rationale described modes as tabs sharing one Roll20 character's attribute pool and framed `k.send` as the mode-to-mode path. That was a misreading: on Roll20 all modes ship in one sheet codebase only because Roll20 allows one sheet per game, and a character never spans modes. The decision (explicit RPC, parent read as the sole exception) is unchanged; the Foundry delivery mechanics are in ADR 0025.
