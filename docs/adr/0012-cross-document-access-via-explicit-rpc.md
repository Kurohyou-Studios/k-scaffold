# Cross-document access is explicit, not shared reads

Roll20's tabs appear to share data only because every tab is literally the same character's attribute pool; modes on Foundry are separate Actor documents, so that sharing is a side effect of the old data model, not a requirement to preserve. Mode-to-mode data needs are therefore handled through the existing `k.send` RPC pattern (`lib/scripts/utility.js`) on both targets: a registered function on the target document is invoked with explicit arguments, rather than one mode reading another's attributes directly. Embedded Items reading their owning Actor's data are the one exception — a genuine parent/child structural relationship — and read transparently through the same alias-layer proxy as the Item's own fields, mirroring how Roll20 sheet-worker code inside a repeating row already reads non-repeating (character-level) attributes through the same flat `attributes` object with no special-casing.
