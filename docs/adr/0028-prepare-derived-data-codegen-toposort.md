# `prepareDerivedData()` codegen: compile-time toposort over `affects`, shared formula evaluator, pure `calculation`

The generated `prepareDerivedData()` body for each Foundry DataModel (one per Actor mode, one per Item type) orders its statements via a **compile-time topological sort** (Kahn's algorithm) over the cascade schema's existing `affects` edges — an edge `A affects B` already means "B depends on A," so it's used directly as a precedence edge with no new graph to build. Roll20's runtime instead drains a FIFO queue per `set()` call with no ordering guarantee and no cycle detection; Foundry's synchronous, non-event-driven `prepareDerivedData()` needs a fixed, correct order baked in, so a **cyclic `affects` graph among derived attributes is now a compile-time build error**, naming the cycle — catching a latent bug class the Roll20 target has always been silently exposed to, rather than carrying it forward.

Each derived attribute's `formula` (declarative macro string, e.g. `@{str}+@{level}`) is *not* statically transpiled into a literal JS expression. Instead, `parseKFormula` is ported into a shared, target-agnostic runtime evaluator called from the generated code, because repeating-section expansion inside a formula is genuinely dynamic (row count varies per document instance) and can't be fully resolved at compile time. `calculation` (a named registered JS function) keeps running as-is through the alias layer, but is now required to be **pure** inside `prepareDerivedData()` — Foundry disallows document writes there — enforced by a runtime dev-mode guard on the alias layer's `set()` (it throws if called while a `prepareDerivedData` context flag is active) rather than static analysis of arbitrary author code. An attribute with **both** `formula` and `calculation` set, which Roll20 silently resolves by letting `calculation` overwrite the formula's result, is now also a compile-time build error: the author must pick one.

`triggeredFuncs` (side-effect functions run on change, not value sources) are explicitly out of scope here — Q4/purity rules them out of `prepareDerivedData()` entirely, and their Foundry equivalent (likely an `_onUpdate`/`_preUpdate` hook) is deferred to its own future ticket.

Cross-document ordering (an Item-level derived attribute feeding an Actor-level one via "parent read") relies on Foundry's own documented lifecycle, which already runs each embedded Item's `prepareDerivedData()` before its owning Actor's — the toposort does not reach across the Actor/Item boundary.
