# Foundry `system` data is flat, numeric attributes are `{ value, max }`, repeating sections are arrays

Foundry imposes no nesting requirement on `system` data beyond `{ value, max }` for token bar attributes (research: [`docs/research/foundry-data-model-nesting.md`](../research/foundry-data-model-nesting.md)). On that basis: actor-level attributes live one level deep as `system.<name>`, named from the mixin call site (ADR 0013). Numeric attributes (the `NumberField`-mapped cases in ADR 0019, including numeric-valued checkboxes) are stored as `{ value, max }` so any of them can become a token bar without a second declaration; non-numeric attributes (`StringField`/`BooleanField`/`HTMLField`-mapped) get a plain field with no `max`, since a bar's `value`/`max` pair must both be numeric and a `max` on a text or boolean field has no meaning to wrap. Repeating sections are `ArrayField`s keyed by section name without the `repeating_` prefix (`system.weapons`, not `system.repeating_weapons`); each row is an object with the same `{ value, max }`/plain-field shape as top-level attributes, plus a scaffold-generated `_id` (itemless rows per ADR 0009 — Item-backed rows per ADR 0006 are unaffected, handled as Foundry's standard embedded Items normally are, with their fields living on the Item's own flat `system`).

`ArrayField` only supports whole-array replacement (no per-index dotted `actor.update()` key, no per-row deletion) — accepted because it's compatible with the batch-once-per-cascade-run flush already settled on #158: the array is reassembled from the in-memory row objects and written once per flush regardless. The cost is real and explicit: two clients editing the same repeating section concurrently last-write-win at the whole-array level, rather than per-row. `TypedObjectField` (v13+) would give per-row addressing and deletion instead, at the cost of losing stable positional ordering as a free property of the storage shape; not adopted here.
