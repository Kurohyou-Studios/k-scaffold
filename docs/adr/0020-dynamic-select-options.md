# Dynamic select options: Roll20-only implementation behind a target-agnostic mixin

`+select` gains a `+dynamicOptions` mixin — a declarative `{section, label}` form (one option per row of a named repeating section) or a custom `{function, trigger}` generator form — to populate options at runtime, resolving the fog item on the Foundry export map ([#154](../../issues/154)). We're implementing and wiring this for Roll20 only: no dynamic `choices` support exists yet in the Foundry `DataField` mapping ([0019](0019-attribute-mixin-datafield-mapping.md)), and building it would be speculative. The mixin's author-facing arguments are deliberately target-agnostic (no Roll20-specific concepts leak into the pug call), so a Foundry backend can be added later without changing sheet-author syntax.

Reactivity is split by what's actually detectable per option-source and target: a row's label change is automatic (the label attribute gets the framework's rebuild function compile-time-injected into its `triggeredFuncs`, rather than an `affects` link, so the select's own `triggeredFuncs` don't fire on a mere rename); row removal is automatic via `+fieldset`'s existing `trigger.triggeredFuncs`; row addition is only detectable via `+customControlFieldset`'s `trigger.addFuncs` (Roll20 fires no native "row added" event), so `+dynamicOptions({section, label})` targeting a plain `+fieldset` section is a compile-time error rather than a silently-incomplete option list. An option generator function must declare its own `trigger.affects` explicitly, since the framework can't infer a freeform function's dependencies the way it can for the declarative form; it may optionally also take a `section` argument purely to opt into the same automatic add/remove wiring, while still supplying its own `{value, label}[]`. Because these references can point at sections declared later in the sheet, validation and injection happen when `+kscript` runs.

Two further consequences of building on `populateListOptions`: its result is not persisted by Roll20, so every dynamic select is rebuilt on `sheet:opened`; and its selector addresses every matching `<select>` on the sheet, so a `+select` inside a repeating section cannot be given dynamic options in v1 (compile-time error) rather than sharing one list and one selected value across rows.

## Considered Options

- **Full cross-target design and implementation now** — rejected: Foundry's own select/`DataField` runtime doesn't exist yet, so implementing a Foundry backend here would be building against an unstable, unbuilt target.
- **Roll20-only implementation with no eye toward Foundry** — rejected: the project's existing pattern is one authored source with per-target backends behind the alias layer; a throwaway Roll20-specific syntax would likely need a breaking author-facing change later.
- **Degrade gracefully when the source section isn't a `customControlFieldset`** (rename/removal work, new rows silently don't appear until sheet reopen) — rejected in favor of a hard compile error: a dynamic list that quietly misses new rows is a worse failure mode than a build-time nudge to add one mixin.
